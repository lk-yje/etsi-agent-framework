视角 1：一条概念性条款如何流转

示例：5.6-6（代码最小化）。它体现“IXIT 多表定位 + recipe 指引 + 证据化裁决”的实际形态，而不是让模型凭空记忆标准。

部分自动 / 概念性 5.6-6 · M1 / phase_B
clause_tool_map.json → phase_definitions.json
IXIT 本地引用与正规化。操作者给受控目录内路径；parse_ixit_xlsx.py 产出 Agent 可消费的 ixit.json，input manifest 固化源路径、hash 与解析摘要。
条款 recipe 在任务层定位。build_clause_recipe_text() 从 clause_tool_map.json 取 5.6-6 的 module、phase、IXIT 表、方法、预期证据、裁决条件与人工边界，放入本次 Phase task。
M1 phase_B 装配知识。共享条款速查 / 能力矩阵 / 裁决表 / 错误库，加 M1 ammo 与 phase 定义的知识，交给 PromptCompiler；模型可通过 bash 查询正规化 IXIT 的多个相关 sheet。
输出结构化 Evidence。必须形成 clauseId、reason、actual/expected、evidence、manualSteps/warnings 等字段；L1 核对结构、条款数、执行痕迹，L2 审计审查结论是否与材料相符。
报告与条款证据包。主 evidence 合并后写入逐条款报告；HTML 以行展开，支持该子条款 / 大条款 / 全部包下载。
当前保证
条款的表定位、方法和裁决参考已由 recipe 和公共知识提供；输入、引用与结论能进入 evidence / audit 链。
当前不保证
尚没有“多 sheet IXIT 检索工具 + 行级引用”的强制调用器。模型获准用 bash 查 JSON，但系统尚未强制每条概念裁决写出精确 sheet/行引用；这是下一步应收敛的适配缺口。

视角 2：一条功能性条款如何流转

示例：5.5-4 未认证访问控制（auth-diff）。这里的重点是“真实 Burp 历史 + 动态 MCP 工具 + 原始回执”，而不是只依据 IXIT 自述。

全自动候选 5.5-4 · M1 / phase_B · Burp auth-diff
auth-diff-workflow.md + clause_tool_map.json
Traffic 先制造可验证流量。双通道启动后，用户通过 Burp 代理登录 DUT 并操作；完成按钮才触发停 xray / tshark、pcap 分析与代理恢复。无 Traffic 不能把空白扫描说成 PASS。
Burp MCP 受令牌与连接条件控制。BURP_MCP_TOKEN 仅注入此次子进程，用于连接本机 BurpMCP 服务；连接成功后动态发现可用工具。无 token / 无连接时，Burp 工具不会注册。
Phase Engine 暴露获准工具。5.5-4 recipe 指明先取认证头，再 auth_diff 比较 authenticated vs none；auth-diff-workflow.md 在 M1 Prompt 中给出双头、保留头、输出字段等操作规则。
ToolRegistry 执行并留回执。模型只可见该 phase 许可的工具；Policy 校验后调用动态 Burp MCP，原始输出和参数形成 tool receipt，随后必须回填条款 evidence。
闸门与审计。L1 先验证 evidence 形状与 trace；M1 Audit 再以 audit-checklist/evidence-standards 判断 response 对比是否真的支持 PASS/FAIL；接受后写 .audit_M1_ACCEPTED。
当前保证
auth-diff 的方法、参数约束、工具白名单、动态发现、执行 policy 与 receipt 留痕已有调用链；真实结果必须进入 evidence 才能进入审计。
当前不保证
“recipe 允许 / 建议 auth_diff”不等于模型必定调用它。MCP 工具是否存在取决于 Burp 连接时发现；目前缺少针对该条款的确定性 auth_diff 强制闸门。缺 Burp/流量时应转为 INCONCLUSIVE / 手工，不应据此 PASS。

视角 3：一份 Skill 在哪里、怎样被引用

以 ETSI report skill 为根，区分编排契约和运行时知识。这正是“物尽其用”而不把所有文件塞进一次 Prompt 的做法。

skills/etsi-ts103701-report/SKILL.md

编排契约

引用位置：Pipeline 状态机、模块拆分、报告阶段、工作区约定的设计来源。

引用方式：不由 PromptCompiler 直接读取；其要求被落实在 pipelines/etsi/pipeline.py、modules.py、phase_definitions.json、contracts/reporting 中。

原因：它描述“怎样编排”，不是一次条款执行时每个模型都应反复阅读的材料。

references/auth-diff-workflow.md

运行时模块知识

引用位置：pipelines/etsi/modules.py 的 M1/M5 ammo_paths。

引用方式：Phase Engine 合并 shared + ammo + phase，写入 AgentConfig.knowledge_paths；PromptCompiler 读取全文，成为 Work Agent 的 system prompt 知识。

隔离：Audit Agent 不加载它，改用 audit-checklist / evidence-standards。

条款 recipe 与 skill 不是替代关系：skill / reference 给“如何做”的长期知识；build_clause_recipe_text() 从 clause_tool_map.json 给“这一次要测哪些 clause、查哪些表、用什么工具、什么证据可裁决”的短任务上下文。二者在 AgentConfig / task 汇合。

工具与脚本：允许、调用、证据三层必须分清

层代码位置含义是否每次必定发生
确定性执行InputManager、TrafficCollectStageIXIT 解析、Traffic 完成后 PCAP 分析由 Python 直接 import / subprocess，并写实际执行结果。是，但取决于触发条件成立
工具可用性ToolRegistry、MCP discovery、phase.tools向该 phase 的 Agent 暴露可调用工具，并经 policy 过滤；Burp MCP 需要令牌和连接。否，只是许可集合

对齐下一步的优先级：不是继续增加无关工具，而是把 5 份 planned_binding 中与真机最直接相关的“固件篡改准备、fallback 决策、harness 约束”逐项接为可观测的确定性边界；同时为概念条款补上多表 IXIT 检索与引用强制，给高价值全自动条款补“关键工具回执必须存在”的 clause gate。

真机迁移时的主体原则（已写入验收包）

不改共享映射表；不为适配结果临时改 skill/recipe；不覆盖同 workspace 的输入或证据；源文件以路径 + hash 引用；实测失败或缺证据要如实保留，必要时新建 workspace。详见 真机迁移验收包/真机阶段变更与证据保全原则.md。

为什么 exploit 资产多数不进入 ETSI 流程？

它们不是“没被发现”，而是按认证范围有意隔离，防止自动升级为未授权的后渗透。与既有 ETSI 条款直接相关的认证、SQLi、XSS、RCE、路径遍历参考已被受限挂载至 M2/M5；其余保留为专项平台资料，需要单独授权才能接入。
