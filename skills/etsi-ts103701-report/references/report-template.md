## 复现逻辑范例

### 功能性测试（5.3.2.2 固件更新明文传输）

```
复现逻辑：

1. 设备连入测试网络，确认 IP 地址（此处为 10.25.243.40）
2. 测试 PC 开启 tshark，选择对应网卡开始抓包
3. 在 DUT Web 界面或云平台触发"检查更新"操作
4. 等待更新流程完成后停止抓包，保存为 update.pcap
5. tshark 过滤栏输入 `http`，定位固件下载请求
6. 在 HTTP GET 请求包上右键 → Follow → TCP Stream
7. 查看 TCP Stream 窗口：

   ┌─────────────────────────────────────────────┐
   │ GET /firmware/SN2502_V1.3.bin HTTP/1.1      │  ← 请求行是 HTTP/1.1
   │ Host: cloud.ceprei.com                      │
   │                                              │
   │ HTTP/1.1 200 OK                             │  ← 响应也是 HTTP/1.1
   │ Content-Type: application/octet-stream       │
   │ [二进制固件数据，无签名头]                     │  ← 无数字签名字段
   └─────────────────────────────────────────────┘

   判定：
   - 协议为 HTTP 明文（非 HTTPS） → 传输未加密
   - 响应中无 X-Signature / Content-Signature 等签名字段 → 无真实性校验
   - 整个会话无 TLS Client Hello / Server Hello → 无加密信道
   
   结论：更新包通过 HTTP 明文传输，无数字签名，MITM 攻击可行 → FAIL
```

### 概念性测试（5.1.2.1 口令生成机制）

```
复现逻辑：

1. 打开 IXIT 1-AuthMech 表格，找到 AuthMech-1 的"口令生成机制"描述
2. 提取关键词：声称的生成方式、口令长度、字符集
3. 实测 DUT 的预装口令：
   - 设备底部标签贴纸上的默认口令：5DFE57
   - 设备铭牌上的设备 ID：B060885DFE57
4. 比对分析：
   - 5DFE57 = B060885DFE57 的后 6 位（位置 7-12）
   - 与 IXIT 声称的"随机生成"矛盾——实为设备 ID 后缀
   - 口令仅 6 位，不符合 NIST SP 800-63B 最低 8 位要求
5. 对照指导书 5.1.2.1 测试单元：
   a) 规律性：ID 后缀递增 → 有规律性 → FAIL
   b) 公共信息关联：与设备 ID 直接相关 → FAIL
   d) 复杂度：6 位长度不足 → FAIL

   结论：口令生成机制与 IXIT 描述多处矛盾，三项测试单元均 FAIL
```
