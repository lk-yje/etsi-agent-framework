## 5.1 不使用通用默认口令

### 5.1-1 唯一口令 (M-shall)

**5.1-1-1 概念性** → PASS:
- 在出厂默认设置以外的任何状态下使用的基于口令的身份验证机制的每个口令都是唯一的，且不是由用户定义的。

**5.1-1-2 功能性** → PASS:
- 在 IXIT 中记录每个已发现的基于口令的身份验证机制；以及
- 要求用户在使用前定义所有口令（这些口令由用户在 IXIT 中定义）；以及
- 没有迹象表明非用户定义的 DUT 口令的生成与 IXIT 中描述的生成机制不同。

---

### 5.1-2 预装唯一口令 (M-shall, 条件性)

**5.1-2-1 概念性** → PASS:
- 没有发现预装口令有明显的规律性；以及
- 在预装口令中没有发现共同字符串或其他共同模式；以及
- 预装口令的生成机制不会生成与公共信息明显相关的口令；以及
- 认为预装口令的生成机制在复杂性方面是适当的。

**escape_clause**: C(2) 条件不满足时 N/A。用户激活时自行设置口令 → N/A 合理。

---

### 5.1-3 认证加密最佳实践 (M-shall) ⚠️

**5.1-3-1 概念性** → PASS:
- 安全保证适合用户身份验证的使用情况；以及
- 该机制适合实现与用例相关的安全保证；以及
- **所有**使用的加密细节都被视为使用案例的最佳做法 (参考 SOGIS)；以及
- **所有**使用的加密细节都不会受到针对特定安全属性的可行攻击。

> 注: MD5、SHA-1 等已被淘汰的算法不能被视为最佳实践密码学。SOGIS 列表: https://www.sogis.eu

**5.1-3-2 功能性** → PASS:
- 没有迹象表明所使用的任何加密设置与其 IXIT 文档不同。

---

### 5.1-4 简单改密机制 (M-shall)

**5.1-4-1 概念性** → PASS:
- 对于所有基于用户的身份验证机制，已发布的资源介绍了如何通过简单的机制更改身份验证值。

**5.1-4-2 功能性** → PASS:
- 用户更改用户身份验证机制的验证值的所有机制均按描述运行。

---

### 5.1-5 防暴力破解 (条件性 M)

**5.1-5-1 概念性** → PASS:
- 所记录的机制使通过网络接口进行暴力攻击变得不可行。

**5.1-5-2 功能性** → PASS:
- IXIT 中记录了曾经发现的基于网络的认证机制；以及
- 对于所有通过网络接口进行的身份验证机制，没有迹象表明暴力防范的实施与其 IXIT 文档有所不同。

**escape_clause**: 如果设备因用例决定的资源限制无法实现 → N/A (需 justification)。

## 5.2 实施管理漏洞报告的方法

### 5.2-1 漏洞披露政策 (M-shall)

**5.2-1-1 概念性** → PASS: 任何人都可以查阅发布的漏洞披露政策。

**5.2-1-2 功能性** → PASS:
- 公开漏洞披露政策；以及
- 包含联系信息 + 确认收到和状态更新的时限信息。

---

### 5.2-2 漏洞及时响应 (R-should)

**5.2-2-1 概念性** → PASS:
- 无迹象表明未对任何类型漏洞及时采取行动；以及
- 确认执行 (IXIT 4-Conf)。

---

### 5.2-3 漏洞持续监控 (R-should)

**5.2-3-1 概念性** → PASS:
- 方法适合持续监测 + 识别 + 纠正安全漏洞；以及
- 确认执行。

## 5.3 保持软件的更新

### 5.3-1 软件组件可更新 (R-should)

**5.3-1-1 概念性** → PASS:
- 对于不具备软件更新能力的所有软件组件，出于实用性或安全原因，不可能进行软件更新；以及
- 更新机制不会被攻击者滥用。

---

### 5.3-2 安全更新机制 (M-shall)

**5.3-2-1 概念性** → PASS: DUT 的更新机制不会被攻击者滥用。

**5.3-2-2 功能性** → PASS:
- 没有迹象表明 DUT 的更新机制可能被滥用。
- (建议: MITM 攻击测试)

---

### 5.3-3 更新简便 (R-should)

**5.3-3-1 概念性** → PASS: 每个软件组件至少有一种更新机制，用户可以轻松使用。

---

### 5.3-4 自动更新机制 (R-should, 条件性)

**5.3-4-1 概念性** → PASS:
- 每个软件组件都有至少一个不需要用户任何交互来执行更新和检查更新的机制；以及
- 对于可配置更新机制，默认至少启用一种自动机制。

**escape_clause**: 不支持自动更新 → 前提不满足 → N/A。

---

### 5.3-5 检查安全更新 (R-should, 条件性)

**5.3-5-1 概念性** → PASS:
- 软件更新可用性检查由 DUT 本身触发；以及
- 在初始化后检查；以及 **定期**检查。

---

### 5.3-6 自动更新配置 (R-should, 条件性) 🔴 最高误判风险

**5.3-6-1 概念性** → PASS:
- DUT 支持自动更新，且用户能启用/禁用/推迟，且初始化状态下已启用
  **或者 DUT 不支持自动更新**；以及
- DUT 支持更新通知，且用户能启用/禁用/推迟，且初始化状态下已启用
  **或者 DUT 不支持更新通知**。

**5.3-6-2 功能性** → PASS:
- 同上结构的 "或者 DUT 不支持" escape 条件。

> 🔴 **这是最常见的误判点。DUT 不支持自动更新/通知 → 直接 PASS。**
> ICS 标 Y 但 IXIT 说不支持 → 文档问题 (M0 观察项)，≠ 功能 FAIL。

---

### 5.3-7 更新加密最佳实践 (M-shall)

**5.3-7-1 概念性** → PASS:
- 安全保证适合安全更新的用例；以及
- **所有**加密细节都是最佳做法 (参考 SOGIS)；以及
- **所有**加密细节都不会受到可行攻击。

> 注: 签名哈希使用 MD5 或 SHA-1 → FAIL。

---

### 5.3-8 安全更新及时性 (M-shall)

**5.3-8-1 概念性** → PASS:
- 管理程序允许及时部署安全更新；以及确认执行。

---

### 5.3-9 验证更新真实性和完整性 (R-should)

**5.3-9-1 概念性** → PASS:
- 每个更新机制都能有效验证真实性 + 完整性；以及
- 验证由 **DUT 本身**执行。

---

### 5.3-10 网络更新信任关系验证 (M-shall)

**5.3-10-1** → PASS:
- 有效验证真实性和完整性；以及
- 验证以有效的信任关系为基础；以及
- IXIT 中记录了每个已发现的基于网络的更新机制。

---

### 5.3-11 通知用户安全更新 (R-should, 条件性) 🟠

**5.3-11-1 概念性** → PASS:
- 通知方法是可识别和明显的；以及
- 通知包括有关更新所减轻的风险的信息。

> 如果设备不支持自动更新检查，则无「待通知的安全更新」场景。
> 此时 ICS 应标 N/A。若 ICS 标 Y 但 IXIT User Notification="None":
> → 严格解读: 无通知机制 → FAIL。
> → 条件解读: 前提不满足 → 应 N/A。

---

### 5.3-12 更新中断通知 (R-should)

**5.3-12-1 概念性** → PASS:
- 通知用户基本功能会被中断；以及通知在 DUT 上实现。

**escape_clause**: 若更新从未中断基本功能 → 无需通知 → PASS。

---

### 5.3-13 发布支持周期 (M-shall)

**5.3-13-1 概念性** → PASS: 支持期限信息易读易懂。

**5.3-13-2 功能性** → PASS:
- 可访问发布资源；访问不受限制；发布了定义的支持期限。

---

### 5.3-14 不可更新说明文档 (R-should, 条件性)

**escape_clause**: 设备可更新 → N/A。

### 5.3-15 不可更新设备隔离 (R-should, 条件性)

**escape_clause**: 设备可更新 → N/A。

### 5.3-16 设备识别信息 (M-shall)

**5.3-16-1 概念性** → PASS: 通过标签或物理接口可清楚识别型号名称。

**5.3-16-2 功能性** → PASS:
- 可根据所述方法提取型号名称；以简单文字提供；与 IXIT 一致。

---

## 5.4 安全存储敏感安全参数

### 5.4-1 安全参数持久存储 (M-shall)

**5.4-1-1 概念性** → PASS:
- 声明与描述一致；安全保证符合最低保护需求；有适当保护机制；未发现不完整。

### 5.4-2 安全参数唯设备硬编码 (R-should, 条件性)

**escape_clause**: 不使用硬编码唯设备标识 → N/A。

### 5.4-3 禁止硬编码关键参数 (M-shall)

**5.4-3-1 概念性** → PASS: 关键安全参数非硬编码。(需固件逆向验证)

### 5.4-4 安全参数唯设备 (R-should)

**5.4-4-1 概念性** → PASS: 升级验证和通信保护的关键安全参数 per-device unique。
注: per-model 共享升级公钥可接受，但需评估批量攻击风险。

## 5.5 安全通信

### 5.5-1 通信加密最佳实践 (M-shall)

**5.5-1-1 概念性** → PASS:
- 安全保证适合通信用例；机制适合实现安全保证；
- **所有**加密细节都是最佳做法 (SOGIS)；**所有**加密细节不会受到可行攻击。

**5.5-1-2 功能性** → PASS:
- **没有迹象表明所使用的任何加密设置与其 IXIT 文档不同。**
- (协议分析器嗅探; 尝试降级攻击)

**5.5-1 裁决逻辑链**:
```
1. IXIT 11-ComMech 声称支持 TLS 1.2/1.3
2. pcap 实测 → 零 TLS, 全 HTTP 明文
3. 加密设置与 IXIT 文档不符 → FAIL
```
注: 应用层加密 (如 ISAPI AES128) 在 IXIT 中有声明时可视为通信加密。
FAIL 理由应精确表述为"实际加密设置与 IXIT 文档不符"，而非笼统的"无加密"。

---

### 5.5-2 经审查的网络安全实现 (R-should) 🔴

**5.5-2-1 概念性** → PASS:
- **审查或评估了网络和安全功能的【所有】实施情况**；以及
- **所有**审查和评估方法均涵盖相关实施范围。

> 🔴 **关键**: 标准要求"所有" (ALL), 不是部分。任何一个 NetSecImpl 条目未经审查 → FAIL。
> "诚实披露未审查" 不构成豁免。IXIT 自述 "It did not review the stack itself" = FAIL 的铁证。

**5.5-2-2 功能性** → PASS:
- 所提供的每个实施方案的名称和版本与报告中一致；或
- 由于 DUT 不提供实施名称和版本信息，无法获取必要信息 (此时也 PASS)。

**裁决逻辑链**:
```
1. IXIT 12-NetSecImpl 声明 2 个实施: Linux kernel + OpenSSL
2. Linux kernel: "It did not review the stack itself" → 未审查
3. OpenSSL: 已审查 (2人) 但版本/范围/方法细节缺失
4. "所有" 条件不满足 → FAIL
```

---

### 5.5-3 加密算法可替换 (R-should)

**5.5-3-1 概念性** → PASS:
- 每个加密软件组件有更新机制；制造商考虑了算法更新的副作用。

### 5.5-4 初始化状态需认证 (M-shall)

**5.5-4-1/2** → PASS: 初始化状态下只有认证后才能访问设备功能。

### 5.5-5 越权防护 (R-should)

**5.5-5-1 概念性** → PASS:
- IXIT 17-PrivlCtrl + 18-AccCtrl 描述了访问控制机制，角色权限设计逻辑自洽。

**5.5-5-2 功能性** → 需三类证据同时 PASS (A + B + 端口):

| 证据 | 来源 | 测什么 |
|------|------|------|
| A — API 越权 | Burp auth_diff (M1) | 全端点 admin vs none 对比，body 相似度 |
| B — 前端加密 | playwright 浏览器 (M2) | 前端加密实现与 IXIT 声明一致（frontend-encryption-check.md） |

**→ PASS**: A 侧全部端点有认证保护 + B 侧前端加密逻辑与 IXIT 一致 + nmap 全端口均在 IXIT 15-Intf 中登记。

**→ FAIL**: A 侧任一端点 body 相似度 >80% 且同为 200；或 B 侧前端加密与 IXIT 不一致；或 nmap 发现未登记端口。

**→ INCONCLUSIVE**: A 侧令牌缺失/端点不足；或 B 侧 playwright 不可用 / 前端加密未测。

### 5.5-6 CSP 传输加密 (R-should, 条件性)

**5.5-6-1** → PASS: 同 5.5-1-1，仅限关键安全参数的通信。

### 5.5-7 远程 CSP 关键安全参数保密 (M-shall, 条件性)

**5.5-7-1 概念性** → PASS:
- 如果存在远程通信机制传输关键安全参数: 应用 5.5-1-1 全部测试单元 + 至少保密性。

**escape_clause**: 没有远程通信机制传输关键安全参数 → N/A。
⚠️ 零 pcap 外连 ≠ 无 Cloud 通信能力。需基于 IXIT Cloud Upgrade 声明综合判断。

### 5.5-8 加密算法可更新管理 (R-should)

**5.5-8-1** → PASS: 安全管理覆盖关键安全参数全生命周期; 确认执行。

## 5.6 尽量减少暴露的攻击面

### 5.6-1 禁用未用接口 (M-shall)

**5.6-1-1 概念性** → PASS:
- 每个标记为启用的接口都有有效的启用理由。

**5.6-1-2 功能性** → PASS:
- 标记为禁用的接口在 DUT 上确实被禁用/无法访问；以及
- **每个被发现的网络和逻辑接口都记录在 IXIT 中。**

> nmap 发现但不在 IXIT 15-Intf 中的开放端口 → 直接 FAIL。

### 5.6-2 最小化未认证信息 (M-shall)

**5.6-2-1 概念性** → PASS:
- 每条安全相关信息都被记录；都是 DUT 运行所必需的。

**5.6-2-2 功能性** → PASS:
- 只能观察到 IXIT 文档中描述的安全相关信息。

### 5.6-3 物理接口保护 (R-should)

**5.6-3-1 概念性** → PASS:
- 物理接口受外壳保护或类似措施；空中接口禁用；非永久接口在不用时禁用。

### 5.6-4 调试接口保护 (M-shall 4A / R-should 4B)

**5.6-4-1/2** → PASS: 调试接口在初始化状态下被禁用或受最佳实践认证保护。

### 5.6-5 最小化软件服务 (R-should)

**5.6-5-1 概念性** → PASS:
- 对于**每一项**默认启用的软件服务，该服务对于 DUT 的预期用途或操作都是必要的。

> IXIT 13-SoftServ 声明禁用但实际启用 → FAIL。
> IXIT 13-SoftServ 未声明的运行中服务 → FAIL。

### 5.6-6 代码最小化 (R-should)
**5.6-6-1** → PASS: 代码最小化技术适合于将代码减少到必要的功能。

### 5.6-7 最小权限 (R-should)
**5.6-7-1** → PASS: 特权控制机制促进职责分离、需知和特权最小化。

### 5.6-8 硬件级内存访问控制 (R-should)
**5.6-8-1** → PASS: 机制在硬件级实施且允许控制对存储器的访问。

### 5.6-9 安全开发流程 (R-should)
**5.6-9-1** → PASS: 安全开发流程覆盖所有阶段。

## 5.7 确保软件的完整性

### 5.7-1 安全启动 (R-should)

**5.7-1-1 概念性** → PASS:
- 信任链完整 (ROM → bootloader → kernel → app)；篡改时尝试恢复。

### 5.7-2 软件完整性检测告警 (R-should)

**5.7-2-1 概念性** → PASS:
- 用户通知方式**足以让用户和/或管理员了解设备软件中未经授权的更改**；以及
- 通知功能都是必要的。

**5.7-2-2 功能性** → PASS:
- 警报实施与 IXIT 文档一致；检测到篡改后通信仅限于必要功能。

> 🔴 **厂商 N/A 逻辑不成立分析**:
> IXIT 20-SecBoot: "Not applicable as there is no notification"
> 这混淆了「没有发生过通知事件」和「不需要通知机制」。
> 设备有检测能力 (secure boot verification 会 fail) 但无告警 → 直接 FAIL。

## 5.8 确保个人数据安全

### 5.8-1 个人数据传输保护 (M-shall, 引用 5.5-1)

**5.8-1-1 概念性** → PASS: 应用 5.5-1-1 全部测试单元 + **至少保密性**。
**5.8-1-2 功能性** → PASS: 应用 5.5-1-2 全部测试单元。

> 5.5-1 FAIL → 5.8-1 继承 FAIL。

### 5.8-2 敏感个人数据传输加密 (条件性)

**5.8-2-1 概念性** → PASS: 应用 5.5-1-1，限制: 设备和相关服务间 + 敏感数据 + 至少保密性。

## 6 消费级物联网产品的数据保护规定

### 6-1 个人数据处理用户信息

**6-1-1 概念性** → PASS: 向消费者提供了适当的个人数据处理信息。

**6-1-2 功能性** → PASS:
- 可如述获得处理个人数据的信息；以及
- 获得的信息与描述相符；以及
- 清晰明确地描述正在处理的个人数据；以及
- 清晰明确地说明使用方式、使用人和使用目的。

---

### 6-2 消费者同意处理个人数据

**6-2-1 概念性** → PASS:
- 描述了如何表示同意；以及
- 自由、明显和明确地做出选择。

**6-2-2 功能性** → PASS: 获得消费者同意的方式与描述相符。

---

### 6-3 撤回消费者同意

**6-3-1 概念性** → PASS: 说明如何随时撤销对个人数据处理的同意。

**6-3-2 功能性** → PASS: 撤销同意的方式与描述相符。

---

### 6-4 遥测数据处理必要性

**6-4-1 概念性** → PASS: 每个遥测数据的处理对于预期功能是必要的。

---

### 6-5 遥测数据处理的用户信息

**6-5-1 概念性** → PASS: 向用户提供了适当的遥测数据处理信息。

**6-5-2 功能性** → PASS:
- 可如述获得遥测数据处理信息；与描述相符；以及
- 描述了正在收集的遥测数据；以及
- 完整描述使用方式、使用人和目的。

## 裁决符号约定

|:---:|------|
| ✅ PASS | 所有结论条件满足 |
| ❌ FAIL | 任一结论条件不满足 |
