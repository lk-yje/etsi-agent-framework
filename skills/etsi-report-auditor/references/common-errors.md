# 常见误判模式与真实案例

> 来源：真实 ETSI TS 103 701 检测记录、裁决审查 pass 经验积累。
> 用法：审计时对照每个 FAIL/条件 PASS 条款检查是否命中以下模式。

---

## 模式 1：escape_clause 被忽略

### 特征

条款是条件性的（M C 或 R C），有明确的 escape 条件（"如果 X 不成立，则此条款不适用/自动通过"）。报告未检查 escape 条件就直接按功能测试判 FAIL。

### 真实案例：5.3-6

```
被审报告裁决：❌ FAIL
理由：设备不支持自动更新开关，无法配置启用/禁用

审计发现：
- 5.3-6 概念性条件："DUT 支持自动更新，且用户能启用/禁用/推迟，且初始化状态下已启用
  或者 DUT 不支持自动更新" → PASS
- IXIT 7-UpdMech 明确写 "Automatic upgrade is not supported"
- escape_clause 适用 → 应判 PASS

审计结论：❌ 误判。裁决应修正为 ✅ PASS。
           ICS 矛盾（标 Y 但功能不支持）→ M0 文档观察项，非功能 FAIL。
```

### 类似条款

| 条款 | escape 条件 | 当 IXIT 说 |
|------|-----------|-----------|
| 5.3-11 | 设备不支持自动检查更新 → N/A | "User Notification: None" |
| 5.1-2 | 不使用预装口令 → N/A | "用户在初始化时自行设置口令" |
| 5.1-5 | 受限设备 → N/A | "Device is constrained per C(5)" |
| 5.3-14 | 设备可更新 → N/A | "All components are securely updateable" |
| 5.3-15 | 设备可更新 → N/A | 同上 |

## 模式 2："所有"条件被放松

### 特征

标准明确要求"所有"(ALL) 实现/接口/加密细节满足某条件。报告只检查了部分就判 PASS。

### 真实案例：5.5-2

```
被审报告裁决：✅ PASS
理由：OpenSSL 已由 2 名安全工程师审查

审计发现：
- IXIT 12-NetSecImpl 列出 2 个实现: Linux kernel + OpenSSL
- Linux kernel: "It did not review the stack itself" → 未审查
- OpenSSL: 已审查但缺少审查范围/版本/方法细节
- 标准要求 "审查或评估了网络和安全功能的所有实施情况"
- Linux kernel 未审查 → "所有"条件不满足

审计结论：❌ 误判。裁决应修正为 ❌ FAIL。
           "诚实披露未审查"不构成豁免。
```

### 类似条款

| 条款 | "所有"条件 | 典型遗漏 |
|------|-----------|---------|
| 5.1-3 | 所有加密细节都是最佳实践 | 只检查了 TLS 没检查前端 JS 加密 |
| 5.3-7 | 同上，针对更新 | 只检查了 TLS 没检查签名算法 |
| 5.5-1 | 同上，针对通信 | 检查了 Web 端口没检查 SDK/RTSP 端口 |
| 5.6-1 | 所有未用接口都已禁用 | nmap TCP 全端口但没扫 UDP |
| 5.6-5 | 所有默认启用的软件服务都必要 | netstat 没看 UDP 监听服务 |
| 5.13-1 | 所有验证方法都有效 | 只测了 Web UI 没测 API |

## 模式 3：ICS/IXIT 矛盾当作功能 FAIL

### 特征

ICS 声明 Y（支持某功能），但 IXIT 详细描述显示功能实际不存在或未实现。报告将此矛盾当作设备功能缺陷 → 判 FAIL。

### 正确处理

这是 ICS 填写质量问题（文档错误），不是 DUT 功能缺陷：
- 功能裁决应基于 DUT 实际能力——DUT 不支持某功能 → 触发 escape_clause → PASS 或 N/A
- ICS 矛盾 → 记录为 M0 文档观察项

### 真实案例：5.3-11 + 5.3-6

```
场景：ICS 标 Y（支持自动更新和通知）
      IXIT 7-UpdMech 写 "Automatic upgrade is not supported"
      IXIT User Notification = "None"

错误裁决：
- 5.3-6: FAIL（"声称支持但未实现自动更新"）
- 5.3-11: FAIL（"声称支持但无通知机制"）

正确裁决：
- 5.3-6: PASS（DUT 不支持自动更新 → escape_clause）
- 5.3-11: N/A（无自动检查 → 无待通知场景 → 条款前提不满足）
- M0 记录：ICS 标 Y 但 IXIT 描述矛盾 → 文档质量观察项
```

## 模式 4：继承关系被忽略

### 特征

条款之间有明确依赖（如 5.8-1 继承 5.5-1 的全部测试单元），但两个条款的裁决不一致且未解释差异。

### 真实案例

```
场景：5.5-1 截获 HTTP 明文通信 → FAIL
      5.8-1 同一设备 → PASS

审计发现：
- 5.8-1 明确引用 5.5-1-1 全部测试单元 + 至少保密性
- 同一抓包文件中，个人数据（如视频流）同样走 HTTP 明文
- 不存在"个人数据走不同加密信道"的证据

审计结论：❌ 裁决矛盾。5.5-1 FAIL → 5.8-1 应继承 FAIL。
          除非能证明个人数据与普通通信走不同加密信道。
```

## 模式 5：证据外推过度

### 特征

证据只覆盖了部分场景，但结论被扩大到全体。典型：pcap 采集期间无外连 → 结论"设备无远程通信能力"。

### 案例 5a：pcap 零外连 ≠ 无 Cloud 能力

```
被审报告裁决：5.5-7 → N/A
理由：pcap 中无设备外连远程服务器的流量 → 无远程 CSP 通信

审计发现：
- IXIT 7-UpdMech 描述 "Cloud-based upgrade service"
- IXIT 24-TelData 列有遥测数据采集
- 此次抓包未触发固件更新检查、未触发遥测上报
- "采集期间无外连" ≠ "设备无远程通信能力"

审计结论：⚠️ 证据外推。裁决不应基于 pcap 的"未发现"。
          应基于 IXIT 声明的远程通信机制，检查实际加密情况。
```

### 案例 5b：某 HTTP 请求明文 ≠ 所有通信明文

```
被审报告裁决：5.5-1 → FAIL
理由：frame 91 POST /ISAPI/ContentMgmt/... HTTP/1.1（明文）

审计发现：
- 仅抓到一个 HTTP 明文请求就下结论"所有通信未加密"
- 未检查其他端口的 TLS 流量（如 RTSP over TLS）
- 未做协议分层统计（tshark -z io,phs）证明"所有通信"
- Nmap 显示 443/tcp 开放，但未验证其 TLS 配置

审计结论：⚠️ 证据不足以支撑"全部通信未加密"的结论。
          至少需要：协议分层统计 + 所有开放端口的 TLS 检查。
```

## 模式 6：N/A 循环论证

### 特征

N/A 的理由是"没发生过"，但条款要求的是"有没有机制"。将"未触发"和"不需要"混淆。

### 真实案例：5.7-2

```
被审报告裁决：N/A
理由：IXIT 20-SecBoot "Not applicable as there is no notification mechanism"

审计发现：
- 设备有安全启动验证能力（5.7-1 声称 support secure boot）
- 检测到篡改后应告警，但无告警机制
- "没有通知机制"正是 FAIL 的理由，不是 N/A 的理由
- 这构成了循环论证："因为没有机制所以不适用，因为不适用所以不需要机制"

审计结论：❌ N/A 理由不成立。设备有检测能力（secure boot）但无告警 → FAIL。
```

### 类似条款

| 条款 | 典型循环论证 |
|------|------------|
| 5.10-1 | "没有遥测数据所以不需要检查" — 但是否真的不收集？ |

## 模式 7：诚实披露当作合规

### 特征

IXIT 中诚实写了"没做/没审查/不知道怎么做的"，报告将此视为"已如实披露"而判 PASS。

### 真实案例

```
被审报告裁决：5.5-2 → PASS
理由：IXIT 已诚实披露使用了哪些安全实现

审计发现：
- IXIT 12-NetSecImpl: "The company used the Linux kernel's networking 
  stack but did not review the stack itself."
- "did not review" = 未审查 ≠ 合规
- 标准要求 "should use reviewed or evaluated implementations"
- 诚实地说没做 ≠ 满足条款

审计结论：❌ 误判。诚实披露不构成合规，应判 FAIL。
```

## 模式 8：元数据查询 ≠ 固件下载

### 特征

在 5.3-2（固件更新明文传输）和 5.3-7（更新加密）中，将固件更新元数据查询（版本检查、升级能力查询等）的 HTTP 明文传输当作"固件以明文传输"的证据。

### 判定前置条件（来自 clause-reference.md）

```
必须先区分「更新元数据查询」和「实际固件下载」：
- 元数据查询（版本检查、升级能力查询等接口）即使走 HTTP 明文 → 
  不能推断固件传输未加密
- 必须观察到实际固件二进制载荷传输（响应体大、Content-Type 为 
  application/octet-stream 或类似二进制 MIME、或 tshark Follow 
  可见固件文件头）→ 才能对传输信道下结论
- 未触发实际下载时 → 标 INCONCLUSIVE
```

### 审计检查

| 检查点 | 是 | 否 |
|--------|:---:|:---:|
| 报告是否区分了"元数据查询"和"固件下载"？ | ✅ | ❌ 证据不充分 |
| 报告是否实际触发了固件下载（非仅版本检查）？ | ✅ | ❌ 应 INCONCLUSIVE |
| pcap 中是否能看到固件文件头/大二进制载荷？ | ✅ | ❌ 元数据不能推论固件传输 |

## 模式 9：流配置参数 ≠ 敏感个人数据

### 特征

在 5.8-2（敏感个人数据传输加密）中，将视频流配置参数（codec、分辨率、码率）当作敏感个人数据进行测试。

### 正确区分

| 属于敏感个人数据 | 不属于敏感个人数据 |
|----------------|------------------|
| 视频流内容（RTP payload） | 流配置参数（codec/分辨率/码率） |
| 音频流内容 | 音频编码格式 |
| 人脸识别数据、POS 交易数据 | 设备元数据 |
| 邮箱地址、手机号 | — |

## 模式 10：pcap 零外连 ≠ 无 Cloud 能力

### 特征

在 5.5-7（远程 CSP 传输加密）中，因 pcap 无外连流量就判 N/A。

### 正确判断流程

```
1. 检查 IXIT 7-UpdMech — 是否有 Cloud-based upgrade？
2. 检查 IXIT 24-TelData — 是否有遥测数据上报？
3. 检查 IXIT 11-ComMech — 是否有远程服务通信声明？
4. 综合判断设备是否具备远程通信能力
5. 如具备 → 需验证 CSP 传输加密（触发对应操作抓包）
6. 如确实不具备 → N/A（附以上检查过程作为 justification）
```

## 审计判定速查表

| 见到的情况 | 审计动作 |
|-----------|---------|
| 5.3-6A/B 判 FAIL | **首先**检查 IXIT 是否写"不支持" → 是 → 误判 |
| 5.5-2 判 PASS | **首先**检查 IXIT 12-NetSecImpl 是否有条目"未审查" → 有 → 误判 |
| 5.8-1 判 PASS 且 5.5-1 判 FAIL | **首先**检查是否同源流量 → 是 → 矛盾 |
| 5.5-7 判 N/A 理由为"pcap 无外连" | **首先**检查 IXIT 是否有 Cloud 声明 → 有 → 证据外推 |
| 5.7-2 判 N/A 理由含"没有通知机制" | **直接判**循环论证 → 误判 |
| 5.3-2/5.3-7 判 FAIL/INCONCLUSIVE | **首先**检查是否区分了元数据查询和固件下载 |
| 任何 PASS 且标准含"所有"(ALL) | **逐项**检查是否覆盖了全部 |
| 任何 NA 理由含"没发生过/没有过" | **直接判**可能循环论证 → 深入检查 |
| 任何 FAIL 无预期 vs 实际对照 | **直接标**证据不足 |
| ICS=Y 的 M 项无测试记录 | **直接标**严重缺陷 |
